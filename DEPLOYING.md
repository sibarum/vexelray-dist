# Deploying VexelRay

How the applications get from the sibling checkouts to the one-line installer. The page users see is
[sibarum.github.io](https://sibarum.github.io), and [README.md](README.md) is the same instructions for this repo;
both are generated, so this file is the one to edit.

```
build.cmd ──► native exes in each app's target\ ──► deploy.ps1 ──► apps\<id>\, install.ps1, README.md   (git)
                                                              ├──► assets\, exe\  ──► -Publish ──► GitHub releases
                                                              └──► ..\sibarum.github.io\  (git, served by GitHub Pages)
```

## What lives where

| Where | What |
| --- | --- |
| each app's `installer.json` (in its own repo) | the app's id, name, version, binary, icon, shortcuts and file types. `repo`, `repoPath` and `releasesRepo` point here |
| `THIRD-PARTY-NOTICES.txt` (in each app's repo, committed) | the third-party software built into that app's exe, with the full licence texts. Installed next to the exe. Generated by `notices/notices.py` |
| `notices/` (here) | `notices.py`, which lists what each exe contains, and the licence texts it copies into the notices files |
| `installer-suite.json` (here) | which apps the suite installs, in order, and where each links to |
| `apps/<id>/` (here, committed) | each app's `install.ps1`, `uninstall.ps1`, `update.ps1`, `manifest.json` and install page |
| `install.ps1`, `README.md` (here, committed) | the suite: runs each app's installer in turn |
| `../sibarum.github.io` (its own repo, committed) | the landing page at https://sibarum.github.io: `index.html`, the icons and screenshots in `img/`, and a copy of the suite's `install.ps1`, so the command is shorter. Generated from `installer-suite.json` (its `site` section, and each member's `image`) |
| releases on `sibarum/vexelray-dist` | the binaries, one release per app version, tagged `<id>-v<version>` (`pix-v0.1.0`) |
| `exe/`, `assets/`, `logs/` (here, ignored) | build output; never committed |
| `preflight/` (here, committed) | the [preflight](#preflight-release) suite installer, pinned to the last snapshots published, and `BUILD.txt` |
| `local/` (here, ignored) | the last preflight's local copy, served from `127.0.0.1` |

`install.ps1` never changes between releases. It reads the app's `manifest.json`, which names each file's
download URL and SHA-256, so publishing a version is: upload the files, then commit the manifests that name them.

The landing page's copy of `install.ps1` differs from this one only in the URL its comment names. Both URLs keep
working: installs and updaters read the manifests from this repo whichever command installed them. The framework's
docs site links to the landing page from `vexelray-framework/docs/install/index.md` and its home page.

## One-time setup

- Every repository checked out side by side in one folder, this one included. `sibarum.github.io` too, or `deploy.ps1`
  skips the landing page with a warning.
- GraalVM 25 as `JAVA_HOME`, and Maven.
- Visual Studio 2026 (18) Community with the C++ workload: native-image links with MSVC's `link.exe` and the icons
  are compiled with `rc.exe`. `build.cmd` sets this up itself with `vcvars64.bat`.
- `imagelib-wrapper`'s native library, built once with a Rust toolchain: `./native/build.sh` in that repo.
- To publish: a **fine-grained** GitHub token, repository access *only* `sibarum/vexelray-dist`, permission
  **Contents: read and write**. Nothing else. `deploy.ps1 -Publish` asks for it; it is never stored.

## Preflight

Everything short of publishing, in one command, from PowerShell (not Git Bash: under Git Bash `vcvars64.bat` fails
and `link.exe` is Git's). It uploads, commits and pushes nothing, so it is safe to run any time:

```powershell
.\preflight.ps1
```

It stops at the first step that fails. Logs are in `logs\`.

1. **build**: `build.cmd` clean-installs the libraries in dependency order with their tests, then tests each app
   and builds its release native image.
2. **start**: starts each app's exe and fails if it is not still running after 8 seconds (`-Seconds` to change).
   The tests run on the JVM, so this is what catches a native image that cannot start, such as one missing a
   resource it never registered in its `reachability-metadata.json` (Vex 0.1.0's own fonts).
3. **notices**: `notices\notices.py --check` writes each app's `THIRD-PARTY-NOTICES.txt` and looks in the exes for
   every component it lists, failing on one that is missing or one it does not list (a new library, say). When it
   fails, add the component to `notices.py` with its licence (in `notices/licenses/`). A changed notices file is
   part of the app's next release; commit it in the app's repo.
4. **versions**: names each app whose `installer.json` version is already published. Bump that app if it changed.
5. **generate**: `deploy.ps1` without `-Publish`, then the files it changed here and in `..\sibarum.github.io`.

After fixing one app, rebuild only it and rerun with `.\preflight.ps1 -SkipBuild`, which uses the exes already in
each app's `target\`.

## Releasing a new version of the apps

1. **Bump the version** in the `installer.json` of each app that changed. A published version is final: its
   release exists, and every install that has it compares against it. Bump the `badge` in `installer-suite.json`'s
   `site` as well (not for a [snapshot](#snapshot-releases)). An app whose version did not change is regenerated identically (only an `updatedAt` stamp moves;
   discard that with `git checkout -- apps`).
2. **Preflight, and look before publishing.**
   ```powershell
   .\preflight.ps1
   git diff
   ```
   The diff should show only the apps you bumped: a new entry in their `manifest.json`, and their pages.
3. **Publish.** Creates each new release and uploads its exe, icon and notices:
   ```powershell
   .\deploy.ps1 -Publish
   ```
4. **Commit, and merge to `main`.** Every installer and updater reads the manifests from `main` (the `branch` in
   each `installer.json`, baked into every generated script), so pushing `develop` alone shows nobody anything. Once
   `main` has them, the install command and every app's updater offer the new version. GitHub's raw host caches for
   a few minutes. Push the landing page as well when it changed (a new app, a new description or screenshot);
   GitHub Pages publishes it within a minute.
   ```powershell
   git add -A; git commit -m "Pix 0.1.1"; git push origin develop
   git checkout main; git merge develop; git push origin main; git checkout develop
   git -C ..\sibarum.github.io add -A; git -C ..\sibarum.github.io commit -m "Pix 0.1.1"; git -C ..\sibarum.github.io push
   ```
5. **Try it** on a machine (or a user account) without the apps:
   ```powershell
   irm https://sibarum.github.io/install.ps1 | iex
   ```

## Snapshot releases

A build off `develop` that can be installed without offering it to anyone: give the apps the poms' snapshot
version (`0.1.1-SNAPSHOT`) in their `installer.json` and release as above, leaving the badge alone.

- `deploy.ps1 -Publish` creates the release `<id>-v0.1.1-SNAPSHOT`, marked as a prerelease on GitHub. Publishing
  the same snapshot again replaces its files, so a snapshot can be rebuilt; a release cannot.
- The manifest lists it, but its `latest` skips prereleases, so the install command and every updater keep offering
  the last release. The manifests still go to `main`: that is the only branch the installers read.
- Install a snapshot with its app's own installer (the suite ignores `INSTALL_VERSION`), adding
  `$env:INSTALL_FORCE = '1'` to take a rebuilt one over the same version:
  ```powershell
  $env:INSTALL_VERSION = '0.1.1-SNAPSHOT'
  irm https://raw.githubusercontent.com/sibarum/vexelray-dist/main/apps/text-editor/install.ps1 | iex
  ```
- A snapshot sorts after the release before it and before its own release, so `update.cmd` leaves it alone until
  `0.1.1` is published, then updates to it. The suite's install command is different: it reinstalls each app's
  `latest` whenever the installed version is not exactly that, so on a machine with snapshots it goes back to the
  last release.
- To release it, change the version to `0.1.1` (and the badge) and release again.

## Preflight release

Every repository built together at its snapshot version, installed with one command, before anything is released.
Double-click **`release-preflight.cmd`** (or run `.\release-preflight.ps1` from PowerShell). It stops at the first
step that fails:

1. **sources**: every repository in `release.py`'s list, and this one, must be on `develop` with nothing
   uncommitted, so the preflight is exactly what was committed. `-AllowDirty` builds anyway, for a local try only:
   such a build is never published.
2. **versions**: if the repositories are still at the release just cut (`0.1.0`), moves them all to the next
   snapshot with `release.py next`. `-NoBump` stops instead. Then each app's `installer.json` gets its pom's version,
   committed in that app's repository.
3. **build**: `preflight.ps1 -BuildOnly`: `build.cmd`, every exe started, the notices checked.
4. **local**: `deploy.ps1 -Local` writes the apps' installers, their releases and the preflight suite into `local\`
   (ignored), all pointing at `http://127.0.0.1:8417` (`-Port`) instead of GitHub. `serve.ps1` serves it, and the
   suite's install command runs in a window of its own: the same scripts as the published preflight, with nothing
   fetched from GitHub. This is a real install on this computer, over the apps already installed. Afterwards each
   app's install record must name its snapshot. The records then point their updaters at `127.0.0.1`, until the
   published preflight or the next release is installed over them.
5. **publish**: asks first, unless `-Publish` was given (`-LocalOnly` stops before it). `deploy.ps1 -Preflight -Publish`
   uploads each app's snapshot release (replacing an earlier build of the same snapshot) and writes `preflight\`:
   the suite installer, pinned to these versions, and `BUILD.txt`, which lists the commit each repository was built
   from. The script then commits, pushes `develop`, merges it to `main` and pushes that. The snapshots are
   prereleases, so the public install command and every updater keep offering the last release. Anyone can install
   the preflight with:
   ```powershell
   irm https://raw.githubusercontent.com/sibarum/vexelray-dist/main/preflight/install.ps1 | iex
   ```
   It reinstalls every app at its pinned snapshot even when that version is already installed, since a snapshot is
   rebuilt under the same version.

To publish a build already tried locally: `.\release-preflight.ps1 -SkipBuild -SkipLocal -Publish`. After a fix to
one app, rebuild only it and run with `-SkipBuild`. To release afterwards, follow
[Releasing a new version](#releasing-a-new-version-of-the-apps) with the versions changed from `X-SNAPSHOT` to `X`.

## Adding an app to the suite

1. Give its repo an `installer.json` like the others: `"repo": "sibarum/vexelray-dist"`, `"repoPath": "apps/<id>"`,
   `"releasesRepo": "sibarum/vexelray-dist"`, `"tagFormat": "<id>-v{version}"`.
2. Add it to `installer-suite.json` (`config` is relative to this folder) and to the app list in `build.cmd`.
   List what its exe contains in `notices/notices.py` (`APPS`), run it, and add
   `{ "name": "notices", "source": "THIRD-PARTY-NOTICES.txt" }` to its `installer.json`'s binaries.
3. Give it an `image` (a screenshot, relative to this folder) and `imageAlt` in `installer-suite.json` if it has one;
   the landing page shows its icon otherwise. Add it to the framework docs' home page, `vexelray-framework/docs/index.md`.
4. Release as above.

## Source releases (tags on every repository)

Separate from the installers, and not needed for every app release. `release.py` cuts a release of all 26
repositories at once, from PowerShell:

```powershell
python release.py release
python release.py next
```

`release` turns each repository's `X-SNAPSHOT` into `X` (in its poms and in the framework's project template),
builds and tests all of them in order, and only when every one has passed commits `Release X` and tags `vX`.
`next` moves each to the next snapshot (`0.1.0` to `0.1.1-SNAPSHOT`), installs it locally and commits. Neither
pushes; push each repository's branch and tag afterwards, for example:

```bash
git push origin main v0.1.0
```

Nothing is deployed to a Maven repository. 0.1.0 (1.0 for atchung, kronometer, tactroller and cardinal; 0.2.0
for supirvast) was cut on 13 October 2026.

## When it goes wrong

- **`'vswhere.exe' is not recognized`** is printed by `vcvars64.bat` and is harmless when the build goes on. If
  native-image then fails to link, the build was started from Git Bash; use PowerShell.
- **`Unable to run 'WindowsDirectives.exe'`**: Windows Application Control blocked one of native-image's probes.
  Run the build again.
- **A test fails at a release version but passed at the snapshot**: something depends on the version ending in
  `-SNAPSHOT`. intrabuf's example did (its payloads are marked dev or release by the version); it now pins its
  snapshot flag instead.
- **A GPU timing test fails now and then**: supirvast's `CompletionTest` compares the fastest of seven runs, since
  an integrated GPU's clocks make single samples useless. If one still fails, it is worth a look, not a retry loop.
- **The suite skips an app as "not published"**: its `manifest.json` is not on `main` yet, or the raw host has not
  caught up. Check `https://raw.githubusercontent.com/sibarum/vexelray-dist/main/apps/<id>/manifest.json`.
