# Deploying VexelRay

How the applications get from the sibling checkouts to the one-line installer. The page users see is
[sibarum.github.io](https://sibarum.github.io), and [README.md](README.md) is the same instructions for this repo;
both are generated, so this file is the one to edit.

```
build.cmd ──► native exes in each app's target\ ───────┐
                                                       ├──► deploy.ps1 ──► apps\<id>\, install.ps1, install.sh, README.md   (git)
build.sh (Linux VM) ──► Linux binaries in target-linux/ ┘               ├──► assets\, exe\  ──► -Publish ──► GitHub releases
                                                                        └──► ..\sibarum.github.io\  (git, served by GitHub Pages)
```

Windows and Linux share a release: an app with a `linux` section in its `installer.json` (Vex, Pix, MainFrame,
Calculator and VexelRay Inspector so far) has its Linux binaries uploaded beside its exe, and its manifest names
both. Its Linux native image is built on Linux: `build.cmd` on the Windows host, `build.sh` in a Linux VM that shares
the folder. On Linux every build goes to `target-linux/` instead of `target/` (each repository's
`linux-build-output` profile), so the two never overwrite each other.

Each operating system is [released on its own](#releasing-a-new-version-of-the-apps), on its own machine, from the
release branch Windows cut: `deploy.ps1 -Platform windows` on Windows, `deploy.sh` in the VM. Each adds its build of
a version to that version's release and manifest, keeping what the others put there. A snapshot
[preflight](#preflight-release) is still built on Windows and published for every platform at once.

## What lives where

| Where | What |
| --- | --- |
| each app's `installer.json` (in its own repo) | the app's id, name, version, binary, icon, shortcuts and file types. `repo`, `repoPath` and `releasesRepo` point here |
| `THIRD-PARTY-NOTICES.txt` (in each app's repo, committed) | the third-party software built into that app's exe, with the full licence texts. Installed next to the exe. Generated by `notices/notices.py` |
| `notices/` (here) | `notices.py`, which lists what each exe contains, and the licence texts it copies into the notices files |
| `installer-suite.json` (here) | which apps the suite installs, in order, and where each links to |
| `apps/<id>/` (here, committed) | each app's `install.ps1`, `uninstall.ps1`, `update.ps1`, `manifest.json` and install page; with a `linux` section, `install.sh`, `uninstall.sh`, `update.sh` and `manifest.linux.txt` too |
| `install.ps1`, `install.sh`, `README.md` (here, committed) | the suite: runs each app's installer in turn. `install.sh` is the Linux one, of the apps that have a `linux` section |
| `../sibarum.github.io` (its own repo, committed) | the landing page at https://sibarum.github.io: `index.html`, the icons and screenshots in `img/`, and copies of the suite's `install.ps1` and `install.sh`, so the commands are shorter. Generated from `installer-suite.json` (its `site` section, and each member's `image`) |
| releases on `sibarum/vexelray-dist` | the binaries, one release per app version, tagged `<id>-v<version>` (`pix-v0.1.0`), with each platform's files added as that platform publishes |
| `exe/`, `assets/`, `logs/` (here, ignored) | build output; never committed. `logs/linux/` is `build.sh`'s, with `BUILD.txt`: the commit of every checkout the Linux binaries were built from, `LOCAL.txt`: the build `local-linux.sh --install` installed, and `REQUEST.txt`, `WATCH.txt`: the preflight's request to the VM's watcher and its answer |
| `preflight/` (here, committed) | the [preflight](#preflight-release) suite installer, pinned to the last snapshots published, and `BUILD.txt` |
| `local/` (here, ignored) | the last preflight's local copy, served from `127.0.0.1` |

`install.ps1` never changes between releases. It reads the app's `manifest.json`, which names each file's
download URL and SHA-256, so publishing a version is: upload the files, then commit the manifests that name them.
`install.sh` is the same on Linux, reading `manifest.linux.txt`, which is written from `manifest.json` because `sh`
cannot read JSON.

The landing page's copy of `install.ps1` differs from this one only in the URL its comment names. Both URLs keep
working: installs and updaters read the manifests from this repo whichever command installed them. The framework's
docs site links to the landing page from `vexelray-framework/docs/install/index.md` and its home page.

## One-time setup

- Every repository checked out side by side in one folder, this one included. `sibarum.github.io` too, or `deploy.ps1`
  skips the landing page with a warning.
- GraalVM 25 as `JAVA_HOME`, and Maven.
- Visual Studio 2026 (18) Community with the C++ workload: native-image links with MSVC's `link.exe` and the icons
  are compiled with `rc.exe`. `build.cmd` sets this up itself with `vcvars64.bat`.
- `imagelib-wrapper`'s native library, built once with a Rust toolchain: `./native/build.sh` in that repo.
- `ffmpeg-wrapper`'s native shim and its pinned FFmpeg, staged once with `./native/build.sh` in that repo.
- To publish: a **fine-grained** GitHub token, repository access *only* `sibarum/vexelray-dist`, permission
  **Contents: read and write**. Nothing else. `deploy.ps1 -Publish` asks for it; it is never stored.

For the Linux binaries, a Linux VM (x86_64, with a desktop session) with the same folder mounted (a VMware shared
folder), and in it:

- GraalVM 25 (with `native-image`), Maven, and what native-image links with: `gcc`, and the zlib and glibc headers
  (`build-essential zlib1g-dev` on Debian and Ubuntu). GraalVM need not be `JAVA_HOME`: `build.sh` finds it when it is
  unpacked into `~/.local/opt`, `/opt` or `/usr/lib/jvm`, or installed by SDKMAN.
- The Linux builds of `imagelib-wrapper`'s native library and `ffmpeg-wrapper`'s shim and FFmpeg, each staged once
  with `./native/build.sh` in the repo's `-linux` module (`imagelib-wrapper-linux`, `ffmpeg-wrapper-linux`).
- A Vulkan driver (Mesa's in a VM), so `build.sh` can start each app.

`./build.sh --check` says what is still missing, in a second. Then, once, from a terminal on the VM's desktop:

```bash
./build.sh --install-watcher
```

which runs `./build.sh --watch` as a systemd user service of every desktop session from then on, so the VM builds
whenever a preflight on Windows asks for it, with nobody at the VM (see [The Linux build](#the-linux-build)).
`--remove-watcher` takes it out again. Nothing is published from the VM, and it needs no token.

## Preflight

Everything short of publishing, in one command, from PowerShell (not Git Bash: under Git Bash `vcvars64.bat` fails
and `link.exe` is Git's). It uploads, commits and pushes nothing, so it is safe to run any time:

```powershell
.\preflight.ps1
```

It stops at the first step that fails. Logs are in `logs\`.

1. **build**: `build.cmd` clean-installs the libraries in dependency order (`vexelray-build`, the plugin that
   stamps every build, first) with their tests, then tests each app and builds its release native image.
2. **start**: starts each app's exe and fails if it is not still running after 8 seconds (`-Seconds` to change).
   The tests run on the JVM, so this is what catches a native image that cannot start, such as one missing a
   resource it never registered in its `reachability-metadata.json` (Vex 0.1.0's own fonts).
3. **linux**: the Linux binaries of each app with a `linux` section. `build.sh`, run in the VM (below), records in
   `logs/linux/BUILD.txt` the commit of every checkout it built; this step fails unless every one of them is still
   the one checked out, and every binary the `linux` sections ship is there. When they are not, the preflight has
   already asked the VM for that build as it started (`logs/linux/REQUEST.txt`), so the VM builds while Windows does,
   and this step waits for the VM's answer. A failed Linux build shows its failing lines here; from a console,
   fix it and press Enter to have the VM build again. Without a watcher in the VM, run from a console, it waits for
   a `./build.sh` started by hand and notices when it is done; otherwise it fails. `-LinuxMinutes` (240) is how long
   it waits.
4. **notices**: `notices\notices.py --check` writes each app's `THIRD-PARTY-NOTICES.txt` and looks in the exes for
   every component it lists, failing on one that is missing or one it does not list (a new library, say). When it
   fails, add the component to `notices.py` with its licence (in `notices/licenses/`). A changed notices file is
   part of the app's next release; commit it in the app's repo.
5. **versions**: names each app whose `installer.json` version is already published. Bump that app if it changed.
6. **generate**: `deploy.ps1` without `-Publish`, then the files it changed here and in `..\sibarum.github.io`.

After fixing one app, rebuild only it and rerun with `.\preflight.ps1 -SkipBuild`, which uses the exes already in
each app's `target\`.

Each OS can also be tried alone, with nothing to coordinate with the other: the Windows preflight below on this
computer, [the Linux preflight](#the-linux-preflight) in the VM. Both end in a real install of the snapshot from a
local copy of the installers. Neither publishes a snapshot: a published preflight carries every platform, so that
still takes the whole preflight above, or the [preflight release](#preflight-release). A release is different: each
platform [releases its own](#releasing-a-new-version-of-the-apps), with `-Platform windows` here or `--release` in
the VM.

### The Windows preflight

For Windows alone, with no Linux VM involved. Double-click **`preflight-windows.cmd`**, or from PowerShell:

```powershell
.\release-preflight.ps1 -WindowsOnly
```

It is the [preflight release](#preflight-release) with the VM left out: the sources and versions steps,
`preflight.ps1 -BuildOnly -WindowsOnly` (build, start and notices, no linux step), then the local install with
`deploy.ps1 -Local -Platform windows`, which generates only the `windows` sections, so no Linux binaries are needed.
It stops there and publishes nothing. `-SkipBuild`, `-SkipLocal` and `-AllowDirty` work as they do there.
`.\preflight.ps1 -WindowsOnly` alone checks without installing: build, start, notices and versions, but no generate
step, since the installers it writes carry every platform.

### The Linux preflight

The same, for Linux alone, in the VM from a terminal on its desktop, with no Windows host needed:

```bash
./preflight.sh
```

It reports each checkout not on `develop` or with uncommitted changes, runs `./build.sh` (build, then start each
app), names each app whose version is already published, and runs `./local-linux.sh --install` (a real install on the
VM, from a local preflight in `~/vexelray-local`). `--skip-build` uses the binaries already built, `--no-local` stops
before the install, and `--skip-tests`, `--seconds` and `--no-start` go to `build.sh`. The notices stay with
`preflight.ps1`, which needs the exes. `--release` is the preflight of a Linux release: every checkout must be on the
release branch, and it ends by generating the Linux installers into `apps/` with `./deploy.sh`.

### The Linux build

With the watcher running in the VM (`./build.sh --install-watcher`, once, or `./build.sh --watch` in a terminal on
its desktop), there is nothing to do: `preflight.ps1` asks for the build, and the watcher runs it and answers.
`logs/linux/watch.log` is the output of the last request, and `logs/linux/WATCH.txt` how it went; the watcher keeps
`logs/linux/watch.alive` fresh so the preflight knows it is there. Stopping the watcher stops a build it is running.
Two builds never run at once in the VM: one started by hand while the watcher builds is refused.

By hand, in the VM, from a terminal on its desktop, in this folder (any time after the last commit; the Windows build
can run at the same time, since the two write to different folders):

```bash
./build.sh
```

It is `build.cmd` for Linux: it clean-installs the same libraries in the same order into the VM's own `~/.m2`
(supirvast's without its tests: they want a real GPU, and the preflight only takes a Linux build of commits Windows
has just tested; `NO_TESTS` in `build.sh` lists them, and `--skip-tests` skips every test), then tests each app that has a `linux` section and builds its native image with `-Pnative-linux` (into `target-linux/`),
then starts each one and fails if it is not still running after 8 seconds (`--seconds`). Logs are in `logs/linux/`.
Only a run in which all of that passed writes `logs/linux/BUILD.txt`. After fixing one app, `./build.sh --only Pix`
(its checkout's name) rebuilds and starts only it, and updates its line. `--skip-build` only starts them, and
`--no-start` skips that, for a VM without a desktop session.

A commit after the build, in any checkout it built, makes the preflight refuse it, since the Linux binaries would no
longer match the exes; build again.

## Releasing a new version of the apps

Windows always goes first: it cuts the release, on a release branch, `release/X` in every repository in
`release.ps1`'s list, cut from `develop`. Every binary, on every platform, names the version in the poms, so the
versions move in lock-step and only here. Each other platform then builds that branch, and publishes the same
version into the same releases, on its own machine and whenever it is ready, however far behind Windows it is. A fix
one platform needs is committed on the branch (and on `develop`), so each platform may be built from a different
commit of it: each binary names the commit it was built from, and the `vX-<platform>` tags say it in the
repositories.

1. **Cut the branch** from `develop`, in every repository in the list, with nothing uncommitted:
   ```powershell
   foreach ($r in (.\release.ps1 status).Repo) { git -C ..\$r branch release/0.1.2 develop }
   ```
2. **Cut the source release** on it ([below](#source-releases-tags-on-every-repository)): every repository is
   switched to the branch, `X-SNAPSHOT` becomes `X`, everything is built and tested, then committed and tagged `vX`:
   ```powershell
   .\release.ps1 release -Branch release/0.1.2
   ```
3. **Bump the version** in the `installer.json` of each app that changed, and commit it on the branch. A published
   version is final: its release exists, and every install that has it compares against it. Bump the `badge` in
   `installer-suite.json`'s `site` as well (not for a [snapshot](#snapshot-releases)).
4. **Windows.** Preflight, look at the diff, publish, then tag what was built:
   ```powershell
   .\preflight.ps1 -Platform windows
   git diff
   .\deploy.ps1 -Publish -Platform windows
   .\release.ps1 deployed -Branch release/0.1.2 -Platform windows
   ```
   The diff should show only the apps you bumped: Windows' part of their version's entry in `manifest.json`, and
   their pages. `-Platform windows` leaves the Linux VM out; what the manifests have for Linux stays as it is.
   `deployed` tags `vX-windows` on each checkout's HEAD and pushes the tags; run it before anything moves the
   checkouts. Then [commit, and merge to `main`](#commit-and-merge-to-main).
5. **Push the branch, and move `develop` on**: `finish` pushes the branch and the `vX` tags, moves each `develop` to
   the next snapshot, and pushes it. After a fix on the branch, `.\release.ps1 publish -Branch release/0.1.2` pushes
   it.
   ```powershell
   .\release.ps1 finish -Branch release/0.1.2
   ```
6. **Linux, when it is ready**, in the VM. The VM shares these checkouts, so put them on the branch first (from
   Windows, `.\release.ps1 switch -Branch release/0.1.2`, and `-Branch develop` after), and pull this repository: the
   publish merges into the manifests Windows committed.
   ```bash
   ./preflight.sh --release
   git diff
   ./deploy.sh --publish
   ```
   `preflight.sh --release` builds the branch, starts each app, installs a local preflight, then generates the Linux
   installers into `apps/` without publishing. `deploy.sh --publish` adds each app's Linux files to the release
   Windows created (or creates it, for a version Windows has not published), and refuses binaries that
   `logs/linux/BUILD.txt` does not name as these checkouts. Then, on Windows,
   `.\release.ps1 deployed -Branch release/0.1.2 -Platform linux` tags `vX-linux` on the commits in `BUILD.txt`, and
   [commit, and merge to `main`](#commit-and-merge-to-main) again.
7. **Try it** on a machine (or a user account) without the apps, on each platform published:
   ```powershell
   irm https://sibarum.github.io/install.ps1 | iex
   ```
   ```bash
   curl -fsSL https://sibarum.github.io/install.sh | sh
   ```

Each installer offers the newest version that has a build for it: Linux's `manifest.linux.txt` names its own, and
the manifest's `latest` is Windows', since every Windows updater already installed reads it. So a version published
for one platform is offered there at once, and nowhere else until it is published there too. A file both platforms
ship under one name (`THIRD-PARTY-NOTICES.txt`) is one upload, so a later platform whose copy differs is refused;
give them the same contents.

macOS has no installer target yet (`vexelray-installer` generates Windows and Linux sections), and no `build.sh` or
`deploy.sh` run there; once it has them, it publishes into the same releases the same way, from a checkout of the
pushed branch.

### Commit, and merge to `main`

After each platform's publish. Every installer and updater reads the manifests from `main` (the `branch` in each
`installer.json`, baked into every generated script), so pushing `develop` alone shows nobody anything. Once `main`
has them, the install command and every app's updater offer the new version. GitHub's raw host caches for a few
minutes. Push the landing page as well when it changed (a new app, a new description or screenshot); GitHub Pages
publishes it within a minute.

```powershell
git add -A; git commit -m "0.1.2 for Windows"; git push origin develop
git checkout main; git merge develop; git push origin main; git checkout develop
git -C ..\sibarum.github.io add -A; git -C ..\sibarum.github.io commit -m "0.1.2 for Windows"; git -C ..\sibarum.github.io push
```

## Snapshot releases

A build off `develop` that can be installed without offering it to anyone: give the apps the poms' snapshot
version (`0.1.1-SNAPSHOT`) in their `installer.json` and release as above, leaving the badge alone.

- `deploy.ps1 -Publish` creates the release `<id>-v0.1.1-SNAPSHOT`, marked as a prerelease on GitHub. Publishing
  the same snapshot again replaces its files, so a snapshot can be rebuilt; a release cannot.
- The manifest lists it, but its `latest` skips prereleases, so the install command and every updater keep offering
  the last release. The manifests still go to `main`: that is the only branch the installers read.
- Install a snapshot with its app's own installer (the suite ignores `INSTALL_VERSION`), adding
  `$env:INSTALL_FORCE = '1'` to take a rebuilt one over the same version:
  ```powershell
  $env:INSTALL_VERSION = '0.1.1-SNAPSHOT'
  irm https://raw.githubusercontent.com/sibarum/vexelray-dist/main/apps/text-editor/install.ps1 | iex
  ```
- A snapshot sorts after the release before it and before its own release, so `update.cmd` leaves it alone until
  `0.1.1` is published, then updates to it. The suite's install command is different: it reinstalls each app's
  `latest` whenever the installed version is not exactly that, so on a machine with snapshots it goes back to the
  last release.
- To release it, change the version to `0.1.1` (and the badge) and release again.

## Preflight release

Every repository built together at its snapshot version, installed with one command, before anything is released.
Double-click **`release-preflight.cmd`** (or run `.\release-preflight.ps1` from PowerShell). It stops at the first
step that fails:

1. **sources**: every repository in `release.ps1`'s list, and this one, must be on `develop` with nothing
   uncommitted, so the preflight is exactly what was committed. `-AllowDirty` builds anyway, for a local try only:
   such a build is never published.
2. **versions**: if the repositories are still at the release just cut (`0.1.0`), moves them all to the next
   snapshot with `release.ps1 next`. `-NoBump` stops instead. Then each app's `installer.json` gets its pom's version,
   committed in that app's repository.
3. **build**: `preflight.ps1 -BuildOnly -LinuxLocal`: `build.cmd`, every exe started, the Linux build checked, the
   notices checked. It asks the VM's watcher for [the Linux build](#the-linux-build) as it starts, after step 2's
   commits, and then for `./local-linux.sh --install` (below), and waits for both. Without a watcher, start
   `./build.sh && ./local-linux.sh --install` in the VM once this step has begun, not before.
4. **local**: `deploy.ps1 -Local` writes the apps' installers, their releases and the preflight suite into `local\`
   (ignored), all pointing at `http://127.0.0.1:8417` (`-Port`) instead of GitHub. `serve.ps1` serves it, and the
   suite's install command runs in a window of its own: the same scripts as the published preflight, with nothing
   fetched from GitHub. This is a real install on this computer, over the apps already installed. Afterwards each
   app's install record must name its snapshot. The records then point their updaters at `127.0.0.1`, until the
   published preflight or the next release is installed over them. `local\` gets the Linux scripts too, but the VM
   cannot reach `127.0.0.1`, so Linux was tried in step 3: `./local-linux.sh --install` writes the same preflight in
   `~/vexelray-local`, pointing at it through `file://`, installs it for real on the VM with nothing fetched from
   GitHub, checks each app's install record names its snapshot, and records that in `logs/linux/LOCAL.txt`, which
   step 3 waits for. `-SkipLocal` skips it on both.
5. **publish**: asks first, unless `-Publish` was given (`-LocalOnly` stops before it). `deploy.ps1 -Preflight -Publish`
   uploads each app's snapshot release (replacing an earlier build of the same snapshot) and writes `preflight\`:
   the suite installer, pinned to these versions, and `BUILD.txt`, which lists the commit each repository was built
   from. The script then commits, pushes `develop`, merges it to `main` and pushes that. The snapshots are
   prereleases, so the public install command and every updater keep offering the last release. Anyone can install
   the preflight with:
   ```powershell
   irm https://raw.githubusercontent.com/sibarum/vexelray-dist/main/preflight/install.ps1 | iex
   ```
   ```bash
   curl -fsSL https://raw.githubusercontent.com/sibarum/vexelray-dist/main/preflight/install.sh | sh
   ```
   It reinstalls every app at its pinned snapshot even when that version is already installed, since a snapshot is
   rebuilt under the same version.

To publish a build already tried locally: `.\release-preflight.ps1 -SkipBuild -SkipLocal -Publish`. After a fix to
one app, rebuild only it and run with `-SkipBuild`. To release afterwards, follow
[Releasing a new version](#releasing-a-new-version-of-the-apps) with the versions changed from `X-SNAPSHOT` to `X`.

## Adding an app to the suite

1. Give its repo an `installer.json` like the others: `"repo": "sibarum/vexelray-dist"`, `"repoPath": "apps/<id>"`,
   `"releasesRepo": "sibarum/vexelray-dist"`, `"tagFormat": "<id>-v{version}"`.
2. Add it to `installer-suite.json` (`config` is relative to this folder) and to the app lists in `build.cmd` and
   `build.sh`. For Linux, give it a `native-linux` profile (`mvn -Pnative-linux package` leaving its binary in
   `target-linux/`, as Vex's does) and a `linux` section in its `installer.json` naming what that leaves; `build.sh`
   builds only the apps that have one. The binary with the shortcuts takes an `"appId"`, its `<groupId>.<artifactId>`
   (or the pom's `vexelray.app.id`), so the dock shows the running app under its icon; the build fails until it does
   (`vexelray-build/README.md`). Choose it before the first release: changing it later renames the installed desktop
   entry, which the installer handles on upgrade (`vexelray-installer/README.md`, Renames), but at a cost to users.
   Its `id` is its `@VexelApp` name, which the build checks. Renaming an app later: change both, list the old name in
   `@VexelApp(formerNames)` and in `installer.json`'s `replaces` with its old `repoPath` (`apps/<old id>`), and keep
   the old `apps/<old id>` folder in this repo, which `deploy.ps1` now refreshes with forwarding copies; take the old
   id out of `installer-suite.json`.
   List what its exe contains in `notices/notices.py` (`APPS`), run it, and add
   `{ "name": "notices", "source": "THIRD-PARTY-NOTICES.txt" }` to its `installer.json`'s binaries.
3. Give it an `image` (a screenshot, relative to this folder) and `imageAlt` in `installer-suite.json` if it has one;
   the landing page shows its icon otherwise. Add it to the framework docs' home page, `vexelray-framework/docs/index.md`.
4. Release as above.

## Source releases (tags on every repository)

`release.ps1` cuts a release of all 28 repositories at once, on the release branch each of them has (see
[above](#releasing-a-new-version-of-the-apps) for cutting it), from PowerShell:

```powershell
.\release.ps1 release -Branch release/0.1.2
```

`release` switches every repository to the branch (once none has uncommitted changes), turns each `X-SNAPSHOT`
into `X` (in its poms and in the framework's project template), builds and tests all of them in order, and only
when every one has passed commits `Release X` and tags `vX`. It pushes nothing, and leaves the checkouts on the
branch. Once the first platform is published (an app's `installer.json` commit after the tag is fine), the rest is
one command:

```powershell
.\release.ps1 finish -Branch release/0.1.2 -DryRun
.\release.ps1 finish -Branch release/0.1.2
```

`finish` is `publish`, then `next`, then a push of each `develop`:

- `publish` checks every repository first: on the branch, nothing uncommitted, HEAD at or after its release tag
  with the poms unchanged since, and nothing on `origin`'s copy of the branch that this one lacks. Any problem stops
  it before anything is pushed. Then each pushes the branch and its tag. `main` and `master` are left where they are.
- `next` switches each to `develop`, still at the `X-SNAPSHOT` the branch was cut at, and once `vX` is tagged moves
  it to the next snapshot (`0.1.2-SNAPSHOT` to `0.1.3-SNAPSHOT`), installs it locally and commits.

Each step runs alone as well, and so do the two that are not part of `finish`: `deployed`, which tags
`vX-<platform>` on what a platform was built from and pushes those tags, and `switch`, which moves every checkout to
a branch. A push that fails part way leaves the repositories before it published; rerun.

Up to 0.1.1, `release` ran on `develop` and `publish` fast-forwarded `main` or `master` to it; those are still at
the 0.1.1 release.

Nothing is deployed to a Maven repository. 0.1.0 (1.0 for atchung, kronometer, tactroller and cardinal; 0.2.0
for supirvast) was cut on 13 October 2026.

`vexelray-build`, the Maven plugin that stamps each build with its source commit, is built first and shares the
stack's version, so `release` and `next` move it and every pom that names it with the rest. It joined the list after
0.1.0 was cut, at `0.1.1-SNAPSHOT`, and so did `ffmpeg-wrapper`, which `vexelray-codec` decodes video with.

## When it goes wrong

- **`'vswhere.exe' is not recognized`** is printed by `vcvars64.bat` and is harmless when the build goes on. If
  native-image then fails to link, the build was started from Git Bash; use PowerShell.
- **`Unable to run 'WindowsDirectives.exe'`**: Windows Application Control blocked one of native-image's probes.
  Run the build again.
- **A test fails at a release version but passed at the snapshot**: something depends on the version ending in
  `-SNAPSHOT`. intrabuf's example did (its payloads are marked dev or release by the version); it now pins its
  snapshot flag instead.
- **A GPU timing test fails now and then**: supirvast's `CompletionTest` compares the fastest of seven runs, since
  an integrated GPU's clocks make single samples useless. If one still fails, it is worth a look, not a retry loop.
- **The suite skips an app as "not published"**: its `manifest.json` is not on `main` yet, or the raw host has not
  caught up. Check `https://raw.githubusercontent.com/sibarum/vexelray-dist/main/apps/<id>/manifest.json`.
